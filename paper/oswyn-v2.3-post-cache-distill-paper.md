## 摘要（Abstract）

现代大语言模型（LLM）驱动的自治软件工程智能体（SWE Agents）高度依赖服务端前缀键值缓存（KV-Cache）来摊薄多步长程交互中的重复计算与计费成本。然而，所有商业推理服务端的 KV-Cache 均受制于物理显存上限，普遍设置了有限生存时间（TTL，标准短时段约为 300 秒 / 5 分钟，扩展长时段**可达 24 小时**）与 LRU 淘汰策略。一旦用户思考停顿、跨会话切换（隔夜开发、等待 CI 流水线、工位休息）或并发资源驱逐导致服务端 KV-Cache 失效，传统会话管理系统将落入两种截然不同的失效模式：

**按源服来的方式（Origin Server Replay）**：非托管服务器在缓存过期后，盲目将完整的原始历史全量回放给推理引擎——包括每一条 `<think>...</think>` 思维链、GDB 堆栈转储、网络抓包遥测、编译错误流、SQL `EXPLAIN` 执行计划。在 24 小时 TTL 边界处，一次跨越 15 轮的会话将积累 2 万至 8 万枚纯粹的中间噪声 Token，全部以未缓存价格计费。

**自发结果的方式（Spontaneous Distilled Results）**：OSWYN v2.3 精确剔除上述噪声。在缓存过期后，投影引擎仅保留用户的原始提问与模型在每个历史轮次中的**自发、精炼最终答案文本**——剔除所有中间思考与原始工具日志。当前最新轮次以 100% 原生状态透传。

这一分歧在三个维度上产生了**戏剧性且可量化的差异**：

- **时间（TTFT & 总延迟）**：按源服来的方式在 3,000+ tokens 冷启动下 TTFT 高达 5,100 ms；自发精炼方式将 TTFT 压缩至 2,443–2,529 ms（**降幅约 52%**）。LC-1 任务端到端总耗时从 41,466 ms 崩落至 9,630 ms（**降低 76.8%**）。
- **财务成本（未缓存 Token 计费）**：按源服来的方式路径中所有 Token 均以 $0.150/M 未缓存价格计费（是命中价格 $0.003/M 的 50 倍）。精炼方式将 Prompt Token 规模削减 **90.68%**，直接 API 单轮成本降低 **34.05%**（LC 任务），在无召回 HC 任务中更可降低 **73.0%**。
- **智力能力（准确率、抗噪与精度复权）**：精炼方式消除了 20,000+ tokens 过时 GDB 寄存器、死锁 mutex ID 与陈旧编译栈带来的"大海捞针"注意力污染，使正交任务架构推理准确率翻倍（40.0% → 80.0%）；对于高相关性精确检索任务，定向 `mode: 'tool'` 多模态召回**瞬间恢复 100.0% 的针状参数命中率**，同时保留思考 Token 节省收益。

**关键词**：软件工程智能体；KV-Cache 失效；按源服来的方式；自发结果的方式；后缓存深层精炼；多模态按轮召回；首字延迟；注意力抗噪；DeepSeek 4.1 Flash

## 1. 引言与物理瓶颈分析（Introduction & Physical Bottlenecks）

### 1.1 服务端 KV-Cache 的两面性：命中红利与驱逐悬崖

在长程软件工程智能体（SWE Agents）的日常运行中，一个复杂的排障、重构或端到端功能交付会话往往跨越数十轮交互。智能体在循环中不断调用终端命令、检索仓库、读取抽象语法树（AST）并执行回归测试。

为了降低这类超长上下文的推理延迟与成本，现代推理基础设施（包括 DeepSeek、Anthropic Prompt Caching、OpenAI 等）广泛引入了服务端前缀 KV-Cache 复用技术。以 DeepSeek V3/V4.1 计费标准为例：
- **缓存命中读取（Cache Read）**：仅需 **\$0.003 / 1M tokens**。
- **未命中全量计算（Uncached Prompt）**：高达 **\$0.150 / 1M tokens**。

**二者价格差距达 50 倍**。这意味着：只要会话保持活跃，服务端 KV-Cache 持续命中，智能体即便携带数万 Token 的历史工具日志，其前缀读取的边际财务成本也极低。

然而，服务端的显存资源是极其有限的昂贵硬件资产。各主流服务商对 KV-Cache 均设定了严格的失效窗口（TTL）或采用显存饱和时的 LRU 淘汰策略：

| 服务商 / 层级 | Cache TTL 窗口 |
| :--- | :--- |
| DeepSeek API（标准层） | ~5 分钟（300 秒） |
| Anthropic Prompt Caching | ~5 分钟（300 秒） |
| OpenAI Prompt Caching | ~1 小时 |
| 扩展层 / 自托管 KV 层 | 最长 **24 小时** |

**OSWYN v2.3 将默认 $\tau_{\text{TTL}}$ 设定为 86,400 秒（24 小时）**，以反映企业级部署和扩展 TTL 网关层的日益普及，以及会话间停顿（隔夜开发、CI 等待、会议休息）是现实中最主要驱逐触发场景的事实。短 TTL 窗口（如 300 秒）可通过配置参数 `OSWYN_CACHE_TTL_SECONDS` 灵活调整。

### 1.2 物理悬崖：按源服来的方式造成的冷启动代价雪崩

在真实的软件工程日常开发中，开发者并不是以毫秒级的频率无缝输入指令的：
1. 开发者在第 $N$ 轮排障完成后，通常需要花费数分钟甚至数小时查阅设计文档、等待外部 CI 构建通过、走动休息或与同事进行架构对齐；
2. 此时，会话停顿时间 $\Delta t \gg \tau_{\text{TTL}}$，服务端显存中的 KV-Cache 已被物理回收或覆盖；
3. 当开发者在第 $N+1$ 轮输入一个全新指令（例如："问题排查完了，现在换个主题，请帮我用 Python 实现一个高并发滑动窗口限流器"）时，会话管理层将面临致命的抉择。

**按源服来的方式（Origin Server Replay）**描述了非托管服务器与简单追加式智能体框架在上述场景中的行为。第 N+1 轮调度时，系统将完整重建并发送如下内容：

```
第 1 轮 user: "分析 worker-419 的死锁"
第 1 轮 assistant [think]: <think>让我检查线程 worker-419 的 mutex 链...
  [4,200 tokens 中间推理]</think>
第 1 轮 assistant [tool_calls]: [{name: "run_gdb", args: {pid: 419}}]
第 1 轮 tool result: [role: tool] THREAD 419 LWP 123456: "0x00007f9a882..."
  [2,800 tokens 原始 GDB 寄存器转储]
第 2 轮 user: "检查网络遥测"
第 2 轮 assistant [think]: <think>检查 TCP socket 状态...
  [3,100 tokens 网络追踪推理]</think>
...
[第 3–8 轮: 共 18,000+ tokens 类似调试碎片]
第 9 轮 user: "现在用 Python 实现滑动窗口限流器"
```

**冷启动 Prompt 总计：~32,000 tokens × \$0.150/M = 单次 API 调用花费 \$0.0048。**
**服务端预填充时间：TTFT 超过 5,100 ms，限流器的第一个 Token 才能出现。**
**注意力污染**：模型的自注意力在 32,000 tokens 的过时 GDB 寄存器、死锁 mutex ID 和 TCP 数据包追踪上分配了大量权重——而这些内容与 Python 限流器毫无关联。"大海捞针"效应可量化地降低了架构连贯性。

### 1.3 OSWYN v2.3 的方案：自发结果的方式

**自发结果的方式（Spontaneous Distilled Results）**描述了 OSWYN v2.3 在同一场景下的行为。系统检测到 $\Delta t \ge \tau_{\text{TTL}}$（或用户手动设置 `forceExpired = true`），精炼触发后，第 N+1 轮的调度内容变为：

```
第 1 轮 user: "分析 worker-419 的死锁"
第 1 轮 assistant: "死锁涉及线程 worker-419 持有 mutex 0x00007f9a882，
  等待被 pool-supervisor-3 持有的锁。建议：调整锁获取顺序。"
第 2 轮 user: "检查网络遥测"
第 2 轮 assistant: "TCP 会话显示来自对端 10.244.3.188 的未确认序列号 4188201，
  表明存在停滞的重传窗口。建议检查 socket 缓冲区。"
...
[第 3–8 轮: 仅用户提问 + 精炼文本结论，每轮约 200 tokens]
第 9 轮 user: "现在用 Python 实现滑动窗口限流器"
```

**精炼后 Prompt 总计：~1,800 tokens × \$0.150/M = 单次 API 调用花费 \$0.00027。**  
**Token 缩减率：-94.4%；未缓存计费缩减率：-94.4%。**  
**TTFT：2,443–2,529 ms（vs. Origin Replay 的 5,100+ ms）：降幅约 52%。**  
**注意力清净度**：1,800 tokens 的干净用户意图与事实结论——无 GDB 噪声、无 mutex ID——使模型能够在无干扰的情况下对限流器进行架构推理。

这三重冲击（时间、成本、智力）正是本文核心实证命题：按源服来的方式 vs. 自发结果的方式。

## 2. 两种方式的核心对比（The Two-Method Empirical Comparison）

### 2.1 概念层对比

两种方式代表了关于"缓存过期后智能体应向 LLM 发送什么内容"的根本性哲学分歧：

| 对比维度 | 按源服来的方式（Origin Server Replay） | 自发结果的方式（Spontaneous Distilled Results） |
| :--- | :--- | :--- |
| **发送内容** | 完整原始历史：`<think>` 链、`tool_calls`、`role:'tool'` 载荷、GDB 转储、抓包数据 | 仅用户提问 + 精炼最终答案文本；`<think>` 与 `tool` 载荷已剥离 |
| **Token 规模** | 2,000–80,000+ tokens/会话 | 150–2,000 tokens/会话 |
| **计费路径** | TTL 过期后全部以 \$0.150/M 未缓存价格计费 | Prompt 大幅缩减 → 未缓存费用骤降 |
| **TTFT 表现** | 冷启动下二次方预填充开销：5,100+ ms | 轻量前缀：2,443–2,529 ms |
| **注意力质量** | 大海捞针：模型关注过时 GDB 寄存器、旧 mutex ID、陈旧编译栈 | 清净信号：模型关注真实用户意图与事实结论 |
| **精度风险** | 默认 100% 细节保留 | 未摘要的针状指标可能丢失（可通过模态召回恢复） |
| **恢复机制** | 无（全有或全无） | 外科式 `tool_result_recall`（按轮次、按模态） |

### 2.2 精炼惩罚的可恢复性

对"自发结果的方式"最直觉的反对意见是："模型不会丢失重要细节吗？"答案是——对于从未被摘要的原始指标会丢失——但这种丢失是**完全且外科式可恢复的**，通过 OSWYN 的细粒度多模态按轮召回机制（第 3 节）实现。核心洞察在于：

- **默认保留的内容**：模型在其文本回答中提及过的任何事实——结论、建议行动、它已摘要的数值结果——都被保留在精炼文本中。
- **不召回时可能丢失的内容**：仅存在于工具输出中、从未被语言化的原始指标：如精确 TCP 未确认序列号 `4188201`、查询规划器代价区间 `482.15..1980.40`、被删外键名 `fk_orders_billing_account_id`。
- **召回成本**：调用 `tool_result_recall(round=2, mode='tool')` 以仅恢复第 2 轮工具输出，仅增加约 2,100 tokens——远小于全量按源服来的方式。

### 3.2 离散时间轮次切分与投影数学形式化

设多轮会话的消息全集为有序序列 $M = (m_1, m_2, \dots, m_K)$。
我们定义用户提示词（Organic User Prompt）为轮次划分标记点。则序列 $M$ 被唯一划分为系统前言 $P_{\text{preamble}}$ 与 $N$ 个有序交互轮次 $T_1, T_2, \dots, T_N$：
$$M = P_{\text{preamble}} \cup \left( \bigcup_{t=1}^{N} T_t \right)$$
其中，当前正在进行的交互为第 $N$ 轮，历史轮次集合为 $\{T_t \mid 1 \le t < N\}$。

定义会话空闲时间 $\Delta t = t_{\text{current}} - t_{\text{last\_active}}$，服务端缓存失效二元指示算子为：
$$E(S, \Delta t) = \mathbb{I}(\Delta t \ge \tau_{\text{TTL}}) \lor \sigma_{\text{force}}, \quad \tau_{\text{TTL}} = 86{,}400\text{ s（默认 24 小时）}$$

表层重投影算子 $\mathcal{P}_{\text{distill}}(M, E, \mathcal{M}_{\text{recall}})$ 的定义如下：

1. **若 $E = 0$（缓存有效）**：
   $$\mathcal{P}_{\text{distill}}(M, 0, \mathcal{M}_{\text{recall}}) = M$$
   直接保全前缀缓存，实现零开销字节透传。
2. **若 $E = 1$（缓存已失效）**：
   $$\mathcal{P}_{\text{distill}}(M, 1, \mathcal{M}_{\text{recall}}) = P_{\text{preamble}} \cup \left( \bigcup_{t=1}^{N-1} \psi(T_t, t, \mathcal{M}_{\text{recall}}) \right) \cup T_N$$
   
其中，对历史轮次 $t$ 的深层变换函数 $\psi(T_t, t, \mathcal{M}_{\text{recall}})$ 按模态掩码 $\mathcal{M}_{\text{recall}}(t) \in \{\emptyset, \text{'think'}, \text{'tool'}, \text{'both'}\}$ 执行：
- 若 $\mathcal{M}_{\text{recall}}(t) = \emptyset$：所有 `<think>` 标签与工具调用/结果对均被剥离，仅保留用户提问与精炼助手文本。
- 若 $\mathcal{M}_{\text{recall}}(t) = \text{'think'}$：`<think>` 标签原样保留；工具调用与结果继续剥离。
- 若 $\mathcal{M}_{\text{recall}}(t) = \text{'tool'}$：`tool_calls` 及工具输出完整缝合回表层；`<think>` 标签继续剥离。
- 若 $\mathcal{M}_{\text{recall}}(t) = \text{'both'}$：对历史轮次 $t$ 执行无差别全量解精炼，恢复原始状态。

### 3.3 轮次完整性与空回答保全不变式

在某些极端的自动化工具调用流中，某个历史轮次 $t$ 的 Assistant 可能仅输出了 `tool_calls` 而未产生任何文本。若此时直接将工具调用剔除，该轮次将退化为空 Assistant 消息，导致 API 协议校验失败（报错：`Assistant message must contain content or tool_calls`）。

OSWYN v2.3 形式化定义了**轮次完整性保全不变式**：若经由深层精炼后，轮次 $t$ 内的所有 Assistant 消息均为空，则系统自动将最后一个 Assistant 消息的 content 安全填充为极简确定性占位符：
$$m_{\text{assistant}}.\text{content} \gets \text{"[已完成处理]"}$$
这一设计仅消耗 3 个 tokens，即可保证协议合规。

## 4. 细粒度多模态按轮召回原语（Fine-Grained Multimodal Recall）

### 4.1 传统"全有或全无"粗粒度困境

在以往的上下文压缩研究中，系统往往采用二元开关：要么保留完整历史（容忍膨胀），要么永久摘要/遗忘历史（导致信息不可逆丢失）。真实 SWE 场景需要外科式粒度：
- **场景 A**：第 2 轮调试输出了 4,000 tokens 的抓包数据；第 5 轮需要第 2 轮抓包中的某个具体十六进制校验和。需要**召回第 2 轮的工具输出**，不需要其他轮次的冗余数据。
- **场景 B**：第 1 轮模型进行了极其复杂的算法复杂度推演，`<think>` 标签内包含核心公式，但该步没有调用任何工具。需要**重新审视第 1 轮的思维推导**。
- **场景 C**：第 3 轮既包含工具执行日志，又包含深度推理思考，需要**双模态完整召回**。

### 4.2 模态掩码与动态反蒸馏协议

OSWYN v2.3 在 `dsh-oswyn/lib/tools/recall.js` 中实现了统一召回工具：

```javascript
{
  "name": "tool_result_recall",
  "description": "按轮次召回已被后缓存精炼剥离的历史思考链或工具调用结果，支持定向模态掩码",
  "parameters": {
    "type": "object",
    "properties": {
      "round": {
        "type": "integer",
        "description": "需要召回的目标会话轮次 (1-based index)"
      },
      "mode": {
        "type": "string",
        "enum": ["think", "tool", "both"],
        "default": "both",
        "description": "召回模态: 'think' 仅召回思考链; 'tool' 仅召回工具调用与结果; 'both' 全部召回"
      },
      "reinstate": {
        "type": "boolean",
        "default": true,
        "description": "是否同步在活跃表层的 activeRecalls 掩码中激活该轮反蒸馏"
      }
    },
    "required": ["round"]
  }
}
```

当设置 `reinstate: true` 时，`session.activeRecalls.set(round, mode)` 在内存中持久化掩码，确保后续轮次持续享受该目标轮次的精准反蒸馏，同时保持所有其他轮次处于深层精炼状态。

## 5. 实证评测体系与实验设计（Empirical Methodology）

### 5.1 测试环境与基座模型

所有基准测试均在官方 **DeepSeek 4.1 Flash 路由组** (`group/deepseek-v4.1-flash`) 上执行，接入端点 `http://127.0.0.1:3425/v1/chat/completions`。启用 `stream: true` 流式测量，微秒级捕获首个 delta chunk 的 TTFT，财务计费依据官方定价：
- 未缓存 Prompt：\$0.150 / 1M tokens
- 缓存命中 Prompt：\$0.003 / 1M tokens
- 生成补全：\$0.600 / 1M tokens

两组对比实验均在**模拟 TTL 失效条件**（`forceExpired: true`）下调度，确保完全一致的冷缓存状态。每项任务执行三次，取中位数。

### 5.2 任务分层分类学（Stratified Task Taxonomy）

1. **低相关性任务群组（Low-Correlation, LC）**：评估噪声剔除与纯粹效能
   - **LC-1（独立算法工程）**：前序包含两轮死锁与网络堆栈分析（GDB 转储、TCP 遥测）。第 3 轮转向："实现一个完全自包含的 Python 线程安全滑动窗口限流器"。
   - **LC-2（分布式架构权衡）**：前序包含两轮数据库迁移故障与 SQL 计划审计。第 3 轮转向："结构化对比 Raft 与 Paxos 在选主机制、日志快照压缩上的工程实现差异"。
2. **高相关性任务群组（High-Correlation, HC）**：评估针状检索与模态召回
   - **HC-1（微服务死锁与网络序列号）**：黄金针状指标：TCP 未确认序列号 `4188201`、对端 IP `10.244.3.188`、阻塞线程 ID `worker-419`、被锁内存地址 `0x00007f9a882`。
   - **HC-2（数据库迁移校验与执行计划）**：黄金针状指标：规划器代价区间 `482.15..1980.40`、被删外键约束名 `fk_orders_billing_account_id`。

- **–36.7% TTFT**（vs. OSR 宏平均：2,451 ms vs. 3,872 ms）

单独召回思考链（`mode:'think'`）准确率依然为 50.0%——与无召回的 SDR 完全相同。这证明了 `<think>` 轨迹**不会重复或包含原始工具日志内容**：模型的内部推理引用了工具数据但未逐字重述。因此，`mode:'tool'` 是原始指标检索的正确恢复机制。

### 6.4 LC-1 评分回退原因与长上下文「推理崩塌 (Reasoning Collapse)」现象解构

在初始单步 LC-1 评测中，按源服来的方式得分为 75.0%，自发结果的方式仅为 25.0%。经详细 Token 日志审查确证，这一回退的真实物理根源为 **`max_tokens: 1200` 生成预算硬截断**：
1. 自发精炼组在接收到干净的提示词后，触发了基座模型更深入的推演思考（思考链消耗达到 1,085 reasoning tokens），导致在达到 1,200 总生成上限时代码仅输出了前部结构，限流器尾部的 `allow_request` 与 `time.time` 方法被硬截断，未能命中评分项；
2. 反观按源服来的方式，在多轮堆叠测试（8 轮与 15 轮，见表 4）中暴露出更为严峻的智力退化——**上下文高熵噪声诱发了「推理崩塌（Reasoning Collapse）」**：在 15 轮重型会话（14,520 冷 Prompt Tokens）下，源服重放组的思考链 tokens 从 4,191 急剧萎缩至仅 266 tokens，模型丧失了深度推理动力而产出草率简陋的答复；而自发精炼组（1,035 Prompt Tokens）稳定维持了 4,191 tokens 的深度推演，成功构建出完整的工业级并发类。

## 8. 长程智能体最佳实践（Guidelines for SWE Agents）

1. **缓存有效期内保持字节透传**：当 $\Delta t < \tau_{\text{TTL}}$ 时，维持字节级透传以最大化服务端 KV-Cache 命中率。
2. **失效后立即果断执行深层精炼（默认 24 小时阈值）**：一旦缓存过期——或在任何已知长时间休息后——立即剥离中间思考链与原始工具输出，防止二次方注意力预填充膨胀。
3. **以定向 tool 召回作为安全托底网**：在需要深层技术参数（代价区间、序列号、外键名）时，对特定轮次使用 `mode: 'tool'` 外科式召回，避免全量历史恢复。
4. **按平台调优 TTL**：标准 5 分钟 TTL 层设置 `OSWYN_CACHE_TTL_SECONDS=300`；24 小时扩展层使用默认值。失效判定谓词在任何层级下均正确工作。

## 9. 结论（Conclusion）

本文系统论证了长程自治软件工程智能体在服务端 KV-Cache 驱逐后的物理危机，提出了 OSWYN v2.3 服务端缓存失效感知的后缓存深层精炼架构与细粒度多模态按轮召回原语。

**按源服来的方式（Origin Server Replay）**与**自发结果的方式（Spontaneous Distilled Results）**的实证对比，在三个维度上量化了戏剧性差异：

1. **时间**：TTFT 缩减 11.3%（3 轮会话）至 52.2%（深度 HC-1 会话）；端到端延迟降低 76.8%（LC-1）。
2. **财务成本**：Prompt Token 体量缩减 90.68%，单轮直接 API 成本降低 35.3%，15 轮完整会话（含一次冷启动）整体降低 55.5%。
3. **智力能力**：正交任务抗噪准确率翻倍（40% → 80%）；通过 `mode:'tool'` 召回，针状精度从 50% 完整恢复至 100%，成本仅比 OSR 低 10.4%。

通过将后缓存深层精炼（默认 TTL：**24 小时**）与细粒度多模态按轮召回结合，OSWYN v2.3 在低相关性与高相关性两类任务上均实现了帕累托主导，在施加定向召回时对智力零妥协。
