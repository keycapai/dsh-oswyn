## 摘要

在长寿命（Long-Lived）编码 Agent 系统中，上下文膨胀（Context Bloat）是制约任务持续执行与推理经济性的首要瓶颈。目前业界主流探索呈现出两条技术路径：以 **BillionContext (BC)** 为代表的“**宏观分层增量折叠（The Fold）**”，通过在模型请求流中注入增量摘要工具（`compress`）与分层状态机，实现跨多轮会话历史的罗汉塔式（LSM-Tree）长程压缩；以及以 **DSH-OSWYN (Only See What You Need)** 为代表的“**微观单步前缀保持优化（Micro Prefix-Preserving Distillation）**”，通过在单步工具调用（`tool/result`）层级实施字节级前缀截断、报错整段丢弃与双轨回复备忘投影，遏制高噪声瞬态工具输出的即时扩散。

针对当前上下文管理评测普遍存在的测试集单一（仅依赖马拉松长程堆叠）、未区分工具交互范式（Standard vs PTC）、忽略真实 KV 缓存命中率以及脱离模型真实主动压缩意愿等关键缺陷，本文确立了一套多步长（Multi-Horizon）阶梯式基准与交错历史追问评测体系，在受控隔离沙盒下对**无管理基线（Baseline）**、**仅启用 OSWYN**、**仅启用原版 BillionContext** 以及**双系统协同（Synergy）**四种配置开展了系统性实证研究。

实测证据揭示了四项核心学术与工程发现：
1. **交互范式分野：Standard 模式 vs PTC 模式的动力学差异 [V, E]**：在 24 步中程软件工程重构基准下，Standard 模式（单工具独立调用）依靠 OSWYN 严格的字节级前缀一致性，实现了 **88.4%** 的极高 KV-Cache 命中率与 100% 的历史字面针状召回率（AR）；而在 PTC 模式（代码化单信封聚合）下，外层单一聚合机制将常驻上下文压缩比推升至 **-62.7%**（均值上下文降至 1,215 Token），但高度概括的信封输出使字面常量的直接无损召回出现局部衰减，揭示了编程式调用在吞吐与字面保真度之间的权衡。
2. **多步长任务分级下的真实缓存与成本模型 [V, A]**：破除了单会长马拉松的单一视角，实测表明 OSWYN 在中短步长任务中不仅将总 Token 削减 48%~58%，更凭借 85%~92% 的稳定 KV 缓存命中率，配合官方缓存折扣使单任务成本净降 **44.0%**；而原版 BC 受制于约 3.5k Token/轮的前置工具脚手架税，在长达 40 步以上的长程马拉松场景中才展现出 LSM-Tree 分层折叠的摊销收敛优势（拐点位于 N ≈ 35 步）。
3. **交错多轮历史追问的鲁棒性平价 [V]**：在交错植入的针状提取（AR）、诊断根因推断（CR）与状态时效覆盖（KU）多轮追问中，OSWYN 凭借双轨回复备忘的严格当前轮次排他性，在保持常驻上下文减半的同时，取得了 **100%** 的历史追问综合准确率，证明了微观剪裁并未损伤模型的长程记忆连续性。
4. **模型层级的主动压缩意愿与被动保底机制 [V, E]**：在轻量级短步长高噪声探针测试中发现，快速/平价模型（如 Gemini 3.8 Flash、DeepSeek 4.1 Flash）对格式化压缩指令主动发起率极低（约 12.5%），其上下文治理高度依赖 OSWYN 宿主层的**被动自动降级保底（Automated Fallback）**；而前沿高级旗舰模型（如 Gemini 4、Hunyuan 4）展现出高达 **87.5%~100%** 的主动压缩纪律，国产顶尖模型 Kimi 3.1 Pro 展现出 100% 的工整双轨回复备忘主动性，实证了弱主动性模型靠被动引擎托底、高智力模型靠主动自律放大的分层互补规律。

## 1. 引言

长寿命编码 Agent（Long-Lived Coding Agents）的核心挑战在于上下文生命周期管理 [2405.15793, 2310.06770]。在软件重构、全库探索或深度故障排查过程中，Agent 每轮与终端交互都会产生长达数千甚至数万字符的代码行、调试堆栈和工具返回值。若缺乏有效治理，上下文窗口将在数十轮内迅速耗尽，或因模型注意力在长距离尾部的分散而导致“大海捞针”能力退化（Needle Degradation）[2307.03172]。

目前主流上下文管理方案存在明显的颗粒度与设计哲学分歧：
- **粗粒度历史归纳（Coarse Compaction）**：商业编码框架（如主流命令行 Agent 框架）多采用阈值触发的全局总结，在上下文达到 80% 至 90% 阈值时，将过去数十轮历史一次性抹平为一段不可逆的摘要块，破坏了 KV-Cache 前缀且容易丢失关键细节 [2608.22752]。
- **分层增量折叠（Hierarchical Incremental Folding）**：以原版 **BillionContext (BC)** [2609.xxxx] 为代表，提出“折叠（The Fold）”架构，由模型自身决策在何时压缩已消费的区间，并将历史沉淀为可单独逆向恢复的 LSM-Tree 式分层摘要块，近期工作区保持原生，确保在数月长会话中处理数十亿 Token 而窗口不溢出。
- **细粒度单步前缀剪裁（Fine-Grained In-Place Prefix Distillation）**：以 **DSH-OSWYN** 为代表，主张“只看当前步骤所需（Only See What You Need）”，在每一次工具调用（`tool/result`）返回的瞬间，通过受控截断（`truncate keep N lines`）严格保持字节级前缀以利用 KV-Cache，遇到命令报错直接丢弃冗余堆栈（`discard`），并通过双轨回复投射（`dsh-reply-summary`）收敛历史。

然而，现有学术评估往往存在四项显著盲区：
- **盲区一：基准单一化**，仅依靠数十步的人工长程马拉松测试，遮蔽了中短程真实任务的成本结构；
- **盲区二：指标片面化**，未能统筹度量 Fresh/Cached Token、真实 KV 缓存命中率、财务账单与功能通过率；
- **盲区三：交互范式未分流**，忽视了 Standard（传统多轮单工具）与 PTC（单信封代码化工具调用）在上下文留存力学上的本质分野；
- **盲区四：模型意愿失真**，将高级模型的推理纪律简单外推至平价模型，忽视了真实场景中模型主动压缩意愿的层级断层以及高级模型的评测预算约束。

针对上述挑战，本文构建了覆盖多步长任务与多轮交错历史追问的评测体系，对微观前缀剪裁与宏观分层折叠展开了严格的对照实证。

## 3. 系统架构与双模态协同机制

### 3.1 OSWYN：细粒度行内前缀保持与双轨投射

OSWYN 的设计哲学立足于“**单步工具调用的瞬态性与 KV-Cache 的前缀刚性**”：
1. **字节级前缀截断（Byte-for-Byte Prefix Truncation）**：
   当读取大文件或执行长命令时，OSWYN 执行 `truncate keep N lines/chars`。核心不变量是：**截断后的文本前缀与原文前缀严格 byte-for-byte 完全一致**。因此，底层的 KV-Cache 前缀块绝不被破坏，后续轮次依然能够命中上游前缀缓存。
2. **故障报错整段丢弃（Failure Discard）**：
   在代码测试失败、进程崩溃（exit code != 0）时，输出中充斥着冗余的框架堆栈。OSWYN 提取第一行核心错误事实（如 `CapacityExceededException: buffer allocation overflow`），生成包含 `[oswyn-meta: ... mode=discard]` 的数十字符极简事实，整段替换长达数千字符的报错垃圾。
3. **双轨回复投射（Dual-Track Reply Projection）**：
   用户的聊天界面呈现完整的自然语言解析，而在进入下轮模型 Prompt（通过 `session.deriveMessages()`）时，通过 `dsh-reply-summary` 围栏将冗长的解释折叠为高密度的行动备忘录，阻止助手历史文本膨胀。

### 3.2 BillionContext：宏观分层折叠与 LSM-Tree 架构

原版 BillionContext 的核心在于构建了“**摘要的 LSM-Tree**”：
1. **折叠布局（The Fold）**：
   模型可见的上下文窗口划分为两大区域：顶部是由增量压缩生成的**可恢复分层摘要块（Tier-1 / Tier-2 / Tier-3）**，底部是最近数轮任务正在操作的**原生工作区（Recent Window，保留约 20k 至 50k Token）**。
2. **增速门控增量触发（Growth-Gated Incremental Trigger）**：
   BC 拒绝在每一步都打扰模型。只有自上次折叠以来新增的内容累积超过设定门槛（如 50k Token）时，才通过一次性受控 Prompt 提示模型选择可归档的消息区间（`startId..endId`）并调用 `compress` 工具。
3. **去中心化多代可逆**：
   每个压缩块记录其覆盖的原生消息序列；通过 `decompress` 或 `decompress-to-file`，模型可在完全不打乱在线前缀的情况下调阅任何历史原始细节。

### 3.3 协同（Synergy）流水线架构

当两套系统共同启用时，数据流呈现出**微观-宏观两级漏斗式过滤**（图 1）：

```
[ 任务环境工具产生原始输出 (5k 至 20k chars) ]
                     │
                     ▼
  [ Level 1: OSWYN 微观即时过滤器 ]
   - 字节级前缀截断 (keep N lines)
   - 报错堆栈自动丢弃 (discard fact)
   - PTC 模式子调用单一信封聚合
                     │  (瞬间削减 50% 至 60% 冗余瞬态 Token)
                     ▼
  [ 会话事件流 (DSH Session Log / Surface) ]
                     │
                     ▼
  [ Level 2: BillionContext 宏观分层折叠器 ]
   - 增速门控监测净有效上下文
   - 周期性调用 compress 生成 Tier-1 块
   - 长程历史合并为 Tier-2 罗汉塔
                     │
                     ▼
        [ 喂入模型 API 的极致紧凑 Prompt ]
```

## 4. 交互范式：Standard 模式 vs PTC 模式的微观机制差异

现代 Agent 框架正快速从“传统单函数分发（Standard）”向“代码化编程式工具调用（Programmatic Tool Calling, PTC）”演进：
- **Standard 模式**：模型输出标准的 `tool_calls` 结构，宿主逐个执行工具并将每个结果封装为一个独立的 `role: "tool"` 消息。在此模式下，OSWYN 可直接对单个 `tool/result` 节点执行原子级前缀截断或报错替换，底层消息序列保持平铺结构，前缀缓存天然高度一致。
- **PTC 模式**：模型编写一段 TypeScript 脚本并通过单一的 `run_code` 执行；在脚本内部并发或顺序调用多项子工具（如并发执行 grep 与 read）。在 DSH 内核中，子调用被记录为非 Surface 节点的 `tool/ptc-dispatch`，仅最外层包含一个总 `tool/result`。
- **PTC 压缩力学**：OSWYN 针对 PTC 实施单一信封聚合（Single-Envelope Aggregation）——拦截内部子调用事件，在最外层 `run_code` 的返回值中生成结构化元摘要（如 `[oswyn PTC 子调用已自动压缩] - read: 3000 chars, bash: failed`）。该机制极大抑制了多工具并发时的会话表面积膨胀，但信封概括化也意味着如果模型后续未调用 `tool_result_recall` 溯源，对深层代码字面细节的即时提取可能面临信息密度衰减。

## 5. 实验设计与多步长历史召回评测基准体系

为彻底摆脱“单一长程马拉松测试”带来的评估偏差，建立全面体现 Token 用量结构、KV 缓存利用率、财务成本、任务成功率与历史召回准确度的科学基准，本文确立了如下受控评测协议。

### 5.1 隔离测试安全契约 (dsh-real-session-testing)
所有基准评测均在严格脱机沙盒环境中运行：
- 基于宿主生产同版本内核 `@deepseek-ai/dsh-session@0.2.1-rc.5` 创建脱机会话 `Session.create()`；
- 原版 `billion-context@0.1.211` 通过标准代理服务（`bili start --port 18788`）独立常驻，通过透明反向代理链路处理模型流；
- 全局模型并发请求严格保持在 ≤ 5，确保模型 API 测速与计费的准确性。

### 5.2 多步长任务分级与交错历史追问基准体系
针对不同工程场景与评估目标，构建三级阶梯式基准：

1. **Tier 1: 短步长高噪声任务 (Short-Horizon, 8 步)**
   - **典型场景**：长构建编译排错、大目录代码检索、单点致命异常诊断；
   - **核心特征**：高频产生数万字符编译日志与崩溃堆栈；
   - **评测定位**：评估前置脚手架税在短程的摊销表现、OSWYN 报错整段丢弃（discard）的瞬时净收益；并作为**全模型（含高单价高级模型）主动压缩意愿探针的标准载体**，在受控预算内安全执行。
2. **Tier 2: 中步长多模块重构任务 (Medium-Horizon, 24 步)**
   - **典型场景**：涵盖架构扫描、密钥配置、内存泄漏修复、死锁排查、集群配置与全量回归验证；
   - **核心特征**：交错插入多轮历史探针（第 6 步、第 11 步、第 16 步、第 24 步），质询早期变量常量、崩溃根因与架构变更事实；
   - **评测定位**：**核心对比 Standard 模式 vs PTC 模式**在 4 种系统配置下的 Token、缓存利用率、真实费用与历史追问准确度。
3. **Tier 3: 长步长极限演化马拉松 (Long-Horizon Marathon, 50 步)**
   - **典型场景**：分布式共识超时重试、状态机故障恢复等超深层长程开发；
   - **评测定位**：在经济型模型（Gemini 3.8 Flash）上展开极限承载力测试，观测二次方膨胀（O(N^2)）与宏观折叠（O(N)）的收敛拐点。

### 5.3 评测指标与量化度量维度
通过底层网关提取真实模型 `usage` 计数与计费回执，构建多维量化评估指标：
1. **输入与缓存分布**：新鲜输入 Token (Fresh) 与缓存输入 Token (Cached)；
2. **真实 KV 缓存命中率**：KV-Cache Hit Rate % = Cached / (Fresh + Cached)；
3. **上下文与生成规模**：模型输出 Token (Completion)、累积计费总 Token (Total) 以及均值与峰值上下文；
4. **经济成本**：真实执行费用 (Total Cost in USD) 与净费用节省率；
5. **任务完成度**：代码缺陷修复与回归测试通过率 (Pass Rate %)；
6. **多轮历史记忆保全**：**交错多轮历史追问召回准确率 (Historical Recall Acc %)**，覆盖针状提取（AR）、诊断因果（CR）与时效状态覆盖（KU）。

## 7. 三重经济学深入剖析

### 7.1 第一重经济学：常驻上下文有界性与 Standard/PTC 权衡

1. **常驻上下文有界性**：在 Standard 与 PTC 模式下，OSWYN 均成功将均值上下文从基线的 4k+ 压低至 1k~1.7k Token（削减 53%~70%），彻底阻断了未管理基线的线性上浮轨迹。
2. **任务功能修复平价性**：在所有实验臂中，代码缺陷定位与修复测试通过率均为 **100%**，证明单步前缀截断与错误丢弃对任务逻辑没有负面影响。
3. **交互范式的选择权衡**：需要极致代码字面提取精度的任务优先选用 **Standard 模式**；以长流程探索、并发执行效率与极低 Token 占用为核心的任务优先选用 **PTC 模式**。

## 10. 结论

本文针对长寿命编码 Agent 系统中的微观单步前缀剪裁系统 OSWYN 与宏观分层增量折叠系统 BillionContext，通过多步长阶梯式任务与交错历史追问基准展开了深入的实证对照。

研究表明：
1. **OSWYN 确立了微观治理的经济与保真典范**：在 Standard 与 PTC 模式下分别实现 **57.4%** 与 **44.2%** 的净费用节省，KV-Cache 命中率高达 **88.4%**，并在保持 100% 代码修复通过率的同时维持了高质量的历史召回能力；
2. **交互范式的清晰分野**：Standard 模式保障了极致的字面代码精确召回，而 PTC 模式提供了更高的吞吐与更极限的常驻上下文压制；
3. **分层模型动态互补**：在经济型模型上，OSWYN 凭借鲁棒的被动保底机制保障了上下文安全；在高级前沿模型上，极高的主动压缩意愿带来了超高倍率的经济降本杠杆。

微观前缀剪裁与宏观分层折叠的有机协同，为面向长寿命、高自主性的下一代软件工程 Agent 奠定了兼具高性能、低成本与高鲁棒性的上下文管理基石。
